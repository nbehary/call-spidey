# M1 — Swift via Eliza

**Goal:** `Normalizer`, `ElizaScript` and `ElizaEngine` exist in
`SpideyCore`, and the 23 ported tests pass under `swift test` on the Mac.

This is a language milestone. There is no UI and no framework beyond
Foundation. The Kotlin tests are your answer key.

itself is `app/src/main/assets/spidey_eliza.json`.

## Order of work

For each of the three files, in the order above:

1. Port the test file to Swift Testing. It will not compile.
2. Write just enough Swift for it to compile. The tests fail.
3. Write the implementation until they pass.
4. Ask for an idiom review.

Do `Normalizer` first: it is one function and seven tests, and it teaches
strings and Regex before anything else is in the way.

## Traps to expect

Each of these will stop you. They are listed so you recognise them, not so
you avoid the work of solving them.

1. **Defaults and decoding.** Kotlin's `val pre: Map<...> = emptyMap()`
   makes a missing JSON key legal. Swift's synthesised `Codable` does not
   use property defaults when a key is absent. Find out what it does
   instead, and what your options are.
2. **Regex and strict concurrency.** `Normalizer` keeps its patterns in a
   stored table. In Swift 6 a shared stored `Regex` will draw a concurrency
   error. Read the error closely; it is your first meeting with `Sendable`.
3. **Injecting randomness.** The Kotlin tests pass a fake `Random` that
   always returns the lowest or the highest value, to force or prevent
   memory recall. Swift's random APIs take a generator differently. Work
   out how the engine can hold one and how a test can supply a fixed one.
4. **String slicing.** Swift strings are not indexed by integers. Most of
   this port can avoid indices entirely; if you find yourself wanting one,
   look for a higher-level method first.
5. **The `$` in `"$none"`.** It needed escaping in Kotlin. Check whether it
   does in Swift.

## Do not port

- The `android`-shaped test file loading (`File(...)` with a working
  directory). Use a package resource.
- Nothing else. This layer has no Android workarounds; port its behaviour
  exactly, including the round-robin cursor and the memory depth.

One test, `everyReassembleLineFitsTheShortTurnTtsBudget`, encodes a limit
that came from Kokoro on Android. Port it anyway: the script is shared, and
M8 brings Kokoro back.

## Explain it back

1. `ElizaEngine` is a `class` in Kotlin. Did you make it a `struct` or a
   `class` in Swift, and what forced the choice?
2. What does your code do when the JSON lacks the `synonyms` key? How do
   you know?
3. Why did the compiler object to a stored `Regex`, and what does your fix
   cost at run time?
4. How do the two fallback tests control the 30 % recall chance?
5. Kotlin has both `ElizaEngine.Reply` and `SpideyResponder.Reply`. You
   will meet the second in M2. Do you expect to need both in Swift?
